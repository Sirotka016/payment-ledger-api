# Архитектура

```text
app/
  core/           общие технические функции: безопасность, JWT, подписи webhook
  models/         SQLAlchemy-модели таблиц
  repositories/   запросы и небольшие операции записи в базу
  routes/         HTTP endpoints Sanic
  schemas/        разбор и проверка входных данных
  services/       бизнес-логика обработки платежного webhook
  config.py       настройки из переменных окружения
  db.py           async engine и фабрика сессий
  main.py         сборка Sanic-приложения

migrations/       Alembic-миграции и стартовые данные
tests/            точечные unit и route tests
```

## Routes

- `auth.py` - вход пользователя и администратора.
- `users.py` - профиль текущего пользователя, его счета и платежи.
- `admins.py` - профиль администратора и управление пользователями.
- `webhooks.py` - webhook внешней платежной системы.

Routes отвечают за HTTP-слой: принять запрос, вызвать нужную логику и вернуть JSON-ответ. Работа с базой вынесена в repositories.

## База данных

В схеме четыре основные таблицы:

- `users`
- `admins`
- `accounts`
- `payments`

Балансы и суммы платежей хранятся через `Numeric(12, 2)` / `Decimal`. Для `payments.transaction_id` задана уникальность, потому что повторный webhook не должен начислять деньги второй раз.

## Payment Webhook

Обработка платежного webhook вынесена в отдельный service, потому что здесь больше бизнес-правил, чем в обычных CRUD endpoints.

Service делает несколько вещей:

- проверяет, была ли транзакция уже обработана;
- проверяет пользователя и счет;
- создает счет, если его еще нет;
- вставляет платеж с учетом идемпотентности;
- атомарно увеличивает баланс счета.

Если webhook приходит повторно с тем же `transaction_id`, API возвращает `already_processed`, а баланс не меняется.
