# Decisions

## App Factory

Приложение собирается через `create_app()`. Так все route-регистрации остаются в одном месте, а тесты могут создавать отдельный экземпляр приложения без запуска отдельного server process.

## Validation

Входные данные разбираются небольшими dataclass-схемами в `app/schemas`. Для текущих payload этого достаточно: формат простой, а отдельная validation-зависимость здесь не дает заметной пользы.

## Auth

Пароли хранятся как PBKDF2-хеши. Login endpoints возвращают JWT access token с `sub` и `role`; защищенные endpoints проверяют ожидаемую роль перед выполнением основной логики.

## Migrations

Схема базы находится в Alembic. Первая миграция также создает стартового пользователя, счет и администратора из требований задания.

## Payment Idempotency

Для webhook ключом идемпотентности выбран `payments.transaction_id`.

Сервис не ограничивается предварительной проверкой в Python. Вставка платежа выполняется через PostgreSQL `ON CONFLICT DO NOTHING`, поэтому повторная транзакция обрабатывается без сырого `IntegrityError` в ответе клиенту.

Баланс увеличивается атомарным SQL-обновлением:

```text
balance = balance + amount
```

Такой вариант защищает от обычной read-modify-write проблемы, когда разные webhook-транзакции приходят на один счет почти одновременно.

## Docker Compose

`docker-compose.yml` поднимает PostgreSQL и API. Контейнер приложения перед стартом Sanic выполняет `alembic upgrade head`, поэтому свежий compose-запуск сразу готовит базу к работе.
