# Implementation Notes

Ниже несколько заметок по решениям, которые я считал важными при выполнении задания.

## Webhook платежей

Webhook принимает данные от внешней платежной системы и пополняет баланс счета пользователя. Основная проверка перед обработкой - SHA256-подпись.

Подпись считается только по данным платежа:

```text
{account_id}{amount}{transaction_id}{user_id}{secret_key}
```

Поле `signature` в расчет не входит. Это важно, потому что иначе подпись зависела бы сама от себя.

Если пользователь не найден, API возвращает `404`. Если счет уже существует, но принадлежит другому пользователю, возвращается `409`. Для повторной транзакции возвращается `already_processed`, баланс повторно не меняется.

## Деньги

Для баланса и суммы платежа используется `Decimal` в Python и `Numeric(12, 2)` в PostgreSQL.

Я не использовал `float`, потому что для денег важна точность. Даже в тестовом задании лучше сразу не закладывать ошибку округления в базовую модель.

## Idempotency

`transaction_id` хранится в таблице `payments` как уникальное поле. Это защищает от повторного начисления, если платежная система отправит один и тот же webhook несколько раз.

В обработке webhook используется PostgreSQL `ON CONFLICT DO NOTHING`. Это позволяет спокойно обработать повторную транзакцию и не возвращать клиенту сырой `IntegrityError`.

Баланс обновляется SQL-выражением:

```text
balance = balance + amount
```

Такой вариант лучше, чем прочитать баланс в Python, прибавить сумму и сохранить обратно. При нескольких платежах на один счет меньше риск потерять обновление.

## Авторизация

После login API возвращает JWT access token. Внутри token есть:

- `sub` - id пользователя или администратора;
- `role` - роль `user` или `admin`.

Перед защищенными endpoints проверяется не только сам token, но и нужная роль. Поэтому пользовательский token не подходит для админских routes, а админский token не подходит для пользовательских endpoints.

## Что можно улучшить в production

Для тестового задания я оставил проект достаточно простым. В production я бы отдельно рассмотрел:

- refresh tokens и более строгую настройку срока жизни JWT;
- централизованный формат ошибок;
- отдельную тестовую PostgreSQL-базу для интеграционных тестов;
- structured logging для webhook;
- rate limit на login endpoints;
- более строгую схему конфигурации и секретов;
- миграции без ручных id там, где это не требуется бизнес-логикой.
